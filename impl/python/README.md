# Python — four implementations, and what separates them

This directory is not one port. It is four, and the differences between them
are the measurements:

- **`slimebench_pure.py`** — no numpy, no tricks. The honest cost of the
  interpreter. Tier B by default, tier A with `--strict-f32`, which costs a
  further 2.2x because CPython has no f32 arithmetic and every intermediate has
  to be forced through a `struct` round-trip.
- **`slimebench_numba.py`** — deliberately the *same program*: the same scalar
  loops, the same order of operations, the same variable names. The only
  difference is `@njit` on the kernels and numpy arrays instead of `array('f')`.
  That makes the pair a controlled experiment, and the ratio between them is
  the cost of the interpreter and nothing else. numba has `float32` as a real
  type, so it is **tier A by default, at no cost** — exactness is free here and
  expensive one runtime away, in the same language.
- **`slimebench_numpy.py`** — the vectorised answer, `deferred` only. It cannot
  do `serial` and refuses the mode with an exit code and a reason rather than
  quietly computing something else: `serial` needs agent *i* to see agent
  *i-1*'s deposit from the same tick, and no numpy expression models that.
  It is also the slowest of the compiled-ish options, which is the finding.
- **`slimebench_mp.py`** — class P for the numpy target, across processes.

Plus two windowed frontends, pygame and raylib-through-cffi.

`--fastmath` on the numba target compiles the identical source text with LLVM's
fast-math flags: one program, one flag, two conformance tiers. It is also not
reliably faster, which is the honest summary.

## Reading order

`slimebench_pure.py` and `slimebench_numba.py` side by side — the point is how
little differs. Then `slimebench_numpy.py` for the contrast in shape, and
`slimebench/common.py` for the shared CLI.

# C# — one source, four ways to compile it

As a language C# is close enough to Java that a second managed-JIT-with-GC row
would add little. What it adds is an axis nothing else in this project has:
**the identical source runs under a tracing JIT and compiles ahead of time to a
native binary with no JIT and no runtime at all.** Stock OpenJDK cannot do
that, so the question "what does the JIT's runtime profile buy over
ahead-of-time compilation?" was unanswerable here until this port existed.

`build.sh` produces four configurations from these files — `jit`, `tier1`,
`r2r`, `aot` — and they must all agree bit for bit.

The answer, briefly: Native AOT lands within a few per cent of the optimising
JIT with a full run's profile behind it, starts seven to nine times faster, and
has no warm-up ramp at all. It also loses the vector unit unless told the
target, which is one flag and a large difference — see §8.

Exactness needs no tricks. Since .NET Core 3.0 `float` arithmetic is strict
IEEE 754 and the JIT may not contract a multiply and an add on its own.

**C# is a barrier problem in class P, and only a barrier problem.** Its compute
scales better than C's; its `System.Threading.Barrier` costs about 2.4 ms per
crossing at thirty-two participants, five times per tick, including the phase
where one thread computes an offset table and thirty-one wait.

## Reading order

`Sim.cs` for the tick and the exactness argument, `Parallel.cs` for class P and
the barrier, `Simd.cs` for `Vector512<float>` against the portable
`Vector<float>` — which will not use AVX-512 on this machine even though the
hardware and the runtime both report it as available.

## Building

```bash
bash impl/csharp/build.sh aot-native
```

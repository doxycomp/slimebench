# Swift — tier A with nothing written differently

Swift's `Float` is IEEE-754 binary32 and the language does not permit the
optimiser to reassociate or to contract a multiply and an add. There is no
`-ffast-math` equivalent on by default, and `Float` arithmetic is specified
operation by operation. `0.94 as Float` is `0x3F70A3D7`, the same bits C's
`0.94f` produces — checked, not assumed.

So unlike C, which needs `-ffp-contract=off`, and Go, which needs an explicit
conversion to forbid fusion, Swift needs nothing. That is a real difference
between the three and worth stating.

**Where the unsafe is, and why.** `Array<Float>` subscripting is bounds-checked
and `-Ounchecked` removes those checks for the whole module — but it also
removes overflow traps on integer arithmetic, and this simulation relies on
`&*` and `&+` wrapping deliberately in the PRNG. Rather than flip a
whole-module switch whose second effect is silent, the hot loops take
`UnsafeMutableBufferPointer` explicitly and the safe variant simply does not.
Both are built and reported side by side, the same way the Rust target is.

Worth noting from the current series: `-Ounchecked` measured *slower* than the
checked build here. Two earlier series put it at a 6 % gain, so the honest
reading is that the flag does not move this program.

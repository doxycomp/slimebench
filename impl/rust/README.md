# Rust — and what the bounds check actually costs

Two indexing strategies from one source, selected at compile time by the
`unchecked` feature, and both are first-class build targets. The point is to
*measure* what bounds checking costs on this workload rather than assert it,
so the harness reports the two side by side and the results section quotes a
number instead of an opinion.

That number is not a constant, which is the more useful finding: the checks
cost a double-digit percentage in the diffusion stencil, where they get in the
way of vectorising, and nothing measurable in the agent pass, where the CPU is
waiting on cache misses anyway. "Bounds checking costs nothing" and its
opposite are both wrong, and this benchmark happens to contain both kinds of
access in one program.

Rust reaches conformance tier A without any flags: it does not contract to FMA
and does not reassociate float expressions, so the arithmetic is right by
default rather than by build configuration. That puts it with Swift and Java,
and against C (which needs `-ffp-contract=off`) and Go (which needs an
explicit conversion).

## Reading order

`src/sim.rs` — the header explains the two indexing strategies and, further
down, the aliasing question that `serial` mode raises: later agents must see
earlier agents' deposits through the same buffer they are reading.

Then `src/parallel.rs` for class P, `src/simd.rs` for class V. The windowed
frontends use the `sdl2` and `raylib` crates rather than a hand-rolled FFI
layer, because that is what a Rust programmer would reach for and therefore
what should be measured.

## Building

```bash
bash impl/rust/build.sh release-native-unchecked
```

`cargo build --release` produces the safe variant directly. The bounds-check
comparison is [docs/RESULTS.md](../../docs/RESULTS.md) §3; class V is §8.
